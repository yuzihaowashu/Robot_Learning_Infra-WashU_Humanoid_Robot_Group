# xr_teleoperate debugging and improvement log
# Date: 2026-03-28
# Project: Robot_Learning_Infra / xr_teleoperate — Unitree G1 + PICO 4U teleoperation

================================================================================
I. Dexterous hand control fix (Dex3-1)
================================================================================

Symptoms:
  - Left hand: middle and index fingers move; thumb does not
  - Right hand: no response at all

Investigation:

  1. Left/right joint directions differ
     The original code used a single DEX3_CLOSE_Q for both hands, but Dex3-1
     right-hand joint directions mirror the left. Split into DEX3_LEFT_CLOSE_Q
     and DEX3_RIGHT_CLOSE_Q with sign flips.
     File: robot_hand_unitree.py

  2. DDS Publisher vs multiprocessing.Process fork conflict (critical pitfall)
     The original code created ChannelPublisher in the main process __init__,
     then used multiprocessing.Process to fork a child running control_process.
     After fork, the DDS socket layer shared the same file descriptor (fd)
     between processes, so the right-hand Publisher’s traffic was effectively
     consumed or interfered with by the main process socket — right-hand
     commands never reached hardware.

     Attempt 1: Create Publisher inside the child → both hands stopped
             (DDS domain isolation between main Subscriber and child Publisher)
     Attempt 2: Restore Publisher in main → left hand OK again, right still dead
     Final fix: Replace multiprocessing.Process with threading.Thread
             Threads share one address space; DDS socket fds are not duplicated
             by fork; both-hand Publishers work.

     File: robot_hand_unitree.py
       - Remove use of Process from multiprocessing
       - Use threading.Thread (daemon=True)

  3. Right-hand hardware encoder fault
     Logs showed a motor in R_state at -238.412 (far out of range) —
     Dex3-1 motor encoder fault; recovered after power cycle.
     Verified with standalone test_right_hand.py (bypass main stack, single-thread DDS).
     Note: In test_right_hand.py use network interface enp2s0, not enp3s0.

  4. Finger gain parameters aligned
     Following Unitree TWIST2 example: finger motors kp=1.0, kd=0.3;
     rebuild HandCmd_ each loop with all fields (mode, q, dq, tau, kp, kd)
     instead of reusing a stale message object.

Outcome:
  All seven motors on both hands respond to trigger control.

III. Arm runaway when starting teleop
================================================================================

Symptoms:
  After pressing Teleoperate, arms snap violently toward joint limits.

Cause:
  Gravity compensation applied feedforward tau to arm joints; in arm_sdk mode
  arm PD is already sufficient — extra tau stacked torques and caused loss of control.

Fix:
  - Apply gravity-compensation tau only to waist joints (12, 13, 14)
  - Keep arm joint tau at 0.0
  File: robot_arm.py → _ctrl_motor_state()

================================================================================
IV. Safe startup: abduct before reaching forward
================================================================================

Symptoms:
  After Teleoperate starts, arms move straight from hang to q=0 (forward reach),
  colliding with or squeezing the torso.

Fix:
  Add safe_deploy (default True) in G1_29_ArmController.__init__:
    Phase 1: Initialize q_target to abducted pose (shoulder roll: left +1.5, right -1.5)
             Arms spread sideways away from body (1.0 s)
    Phase 2: Update q_target to np.zeros(14) (forward reach), smooth blend (1.0 s)

  Path: hang → abduct → forward reach, avoiding the front of the body.
  File: robot_arm.py → G1_29_ArmController.__init__

================================================================================
V. Safe shutdown when stopping teleop
================================================================================

Symptoms (early):
  After Stop Teleop, arms drop from current pose too fast (motors release abruptly),
  risking torso impact.

Fix:
  Rewrite ctrl_dual_arm_go_home() as a three-phase shutdown:
    Phase 1: Abduct (1.0 s) — spread arms away from body
    Phase 2: Move to q=0 forward pose (up to 2.0 s)
    Phase 3: Ramp arm_sdk weight 1.0 → 0.0 slowly,
             201 steps × 20 ms ≈ 4.0 s; arms lower gently under gravity
  File: robot_arm.py → ctrl_dual_arm_go_home()

================================================================================
VI. Gradio panel — Relax Arms button
================================================================================

Requirement:
  After teleop, arms may stay in forward reach (motors locked).
  Need a button to relax arms safely to a natural hang.

Implementation:
  Gradio panel adds "Relax Arms", calling reset_arms():
    1. Read current arm joints; if all |q| < 0.15 rad, consider already relaxed
       and return (avoid getting stuck in abduct on repeated clicks)
    2. Otherwise create G1_29_ArmController(safe_deploy=False) and call
       ctrl_dual_arm_go_home() for the three-phase release

  Run via subprocess.run in a separate process to avoid DDS clashes with Gradio.
  Timeout 20 s.
  File: gradio_panel.py → reset_arms()

================================================================================
VII. Process management — SIGHUP
================================================================================

Symptoms:
  After Stop Teleop from Gradio, the teleop child was killed by SIGHUP before
  finishing safe shutdown (go_home).

Fix:
  At top of teleop_hand_and_arm.py:
    signal.signal(signal.SIGHUP, signal.SIG_IGN)
  Ignore SIGHUP so the child can complete shutdown after the parent exits.
  File: teleop_hand_and_arm.py

================================================================================
VIII. Network interface configuration
================================================================================

Pitfall:
  Unitree DDS must use the correct interface name.
  This machine’s Ethernet is enp2s0 (not enp3s0).
  ChannelFactoryInitialize(0, "enp2s0") — second argument must match.
  If wrong, DDS may report "does not match an available interface" and fail quietly:
  published data never reaches the robot.

================================================================================
X. Lessons learned
================================================================================

  1. DDS + multiprocessing.Process is a major footgun
     DDS keeps socket fds; after fork parent and child share the same fd,
     Publisher behavior becomes unpredictable. Prefer threading.Thread.

  2. Apply gravity compensation selectively
     In arm_sdk mode arm PD is enough; do not stack gravity tau on arms
     or torques blow up. Reserve gravity comp for waist / similar joints.

  3. Safe motion sequences matter
     On start and stop use "abduct → target → release" transitions;
     otherwise straight-line motion cuts through the body.

  4. Hardware faults: absurd motor state values (e.g. -238); power cycle may fix.

  5. Wrong interface name: DDS may not fail loudly but traffic is dead — check first.

  6. SIGHUP: Gradio subprocess children get SIGHUP when parent exits;
     ignore explicitly if cleanup must run.

  7. Relax Arms must read state: if already relaxed, do not re-take control
     and abduct again or you pull a relaxed arm up and jam it.
