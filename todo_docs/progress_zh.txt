# xr_teleoperate 调试与改进记录
# 日期: 2026-03-28
# 项目: Robot_Learning_Infra / xr_teleoperate — Unitree G1 + PICO 4U 遥操作

================================================================================
一、灵巧手控制修复 (Dex3-1)
================================================================================

【问题现象】
  - 左手：中指、食指能动，拇指不动
  - 右手：完全不响应

【排查过程】

  1. 左右手关节方向不一致
     原代码用统一的 DEX3_CLOSE_Q 控制左右手，但 Dex3-1 的右手关节方向与左手
     镜像。拆分为 DEX3_LEFT_CLOSE_Q 和 DEX3_RIGHT_CLOSE_Q，正负方向取反。
     文件: robot_hand_unitree.py

  2. DDS Publisher 与 multiprocessing.Process 的 fork 冲突（关键坑）
     原代码在主进程 __init__ 中创建 ChannelPublisher，然后用
     multiprocessing.Process fork 子进程执行 control_process。
     DDS 底层 socket 在 fork 后被两个进程共享同一个文件描述符(fd)，
     导致右手的 Publisher 实际发出的数据被主进程的 socket 回收/干扰，
     右手命令从未真正到达硬件。

     尝试 1: 把 Publisher 移到子进程内创建 → 两只手都不动了（主进程的
             Subscriber 和子进程的 Publisher 之间 DDS 域隔离）
     尝试 2: 改回主进程创建 Publisher → 恢复左手能动、右手不动
     最终修复: 把 multiprocessing.Process 改为 threading.Thread
             线程共享同一地址空间，DDS socket fd 不会被 fork 复制，
             左右手 Publisher 均正常工作。

     文件: robot_hand_unitree.py
       - 删除 from multiprocessing import Process 中的 Process 使用
       - 改为 threading.Thread（daemon=True）

  3. 右手硬件 Encoder 错误
     日志中发现 R_state 某个电机值为 -238.412（远超正常范围），
     属于 Dex3-1 电机编码器故障，断电重启后恢复。
     通过独立脚本 test_right_hand.py 验证（绕过主框架、单线程 DDS 直连）。
     注意: test_right_hand.py 中网络接口要用 enp2s0 而非 enp3s0。

  4. 手指增益参数对齐
     参考 Unitree TWIST2 示例，将手指电机 kp=1.0, kd=0.3，
     每个循环重新构造 HandCmd_ 消息并设置全部字段（mode, q, dq, tau, kp, kd），
     而非复用旧消息对象。

【最终结果】
  左右手全部 7 个电机均能响应扳机控制。

================================================================================
三、启动遥操作时手臂失控
================================================================================

【问题现象】
  按下 Teleoperate 后，手臂会猛烈甩到关节极限。

【原因】
  重力补偿 (Gravity Compensation) 对手臂关节施加了 feedforward tau，
  而 arm_sdk 模式下手臂 PD 控制已经足够，额外 tau 导致力矩叠加失控。

【修复】
  - 只对腰部关节 (joint 12, 13, 14) 施加重力补偿 tau
  - 手臂关节 tau 保持 0.0
  文件: robot_arm.py → _ctrl_motor_state()

================================================================================
四、安全启动：手臂先外展再前伸
================================================================================

【问题现象】
  Teleoperate 启动后手臂直接从自然下垂移向 q=0（前伸），
  过程中双手会撞击/挤压身体。

【修复】
  在 G1_29_ArmController.__init__ 中增加 safe_deploy 参数（默认 True）:
    Phase 1: q_target 初始化为外展姿态 (shoulder roll: 左+1.5, 右-1.5)
             手臂先向两侧展开，远离身体（1.0 秒）
    Phase 2: q_target 更新为 np.zeros(14)（前伸姿态），平滑过渡（1.0 秒）

  这样手臂从下垂 → 外展 → 前伸，全程不经过身体正面。
  文件: robot_arm.py → G1_29_ArmController.__init__

================================================================================
五、停止遥操作时的安全退出
================================================================================

【问题现象（早期）】
  Stop Teleop 后手臂直接从当前姿态掉落（电机释放太快），可能撞身体。

【修复】
  重写 ctrl_dual_arm_go_home()，三阶段退出:
    Phase 1: 先外展（1.0 秒）— 手臂向两侧展开，离开身体
    Phase 2: 移到 q=0 前伸位（最多 2.0 秒）
    Phase 3: 缓慢释放 arm_sdk 权重，从 1.0 → 0.0，
             201 步 × 20ms = 约 4.0 秒，手臂在重力下缓慢放下
  文件: robot_arm.py → ctrl_dual_arm_go_home()

================================================================================
六、Gradio 面板 — Relax Arms 按钮
================================================================================

【需求】
  Teleop 结束后手臂可能仍保持前伸姿态（电机锁定），
  需要一个按钮让手臂安全放松到自然下垂。

【实现】
  Gradio 面板添加 "Relax Arms" 按钮，调用 reset_arms():
    1. 先读取当前手臂关节角度，如果所有关节 |q| < 0.15 rad，
       说明已经放松，直接返回（避免重复操作时卡在外展位）
    2. 如果未放松，创建 G1_29_ArmController(safe_deploy=False)，
       调用 ctrl_dual_arm_go_home() 执行三阶段安全释放

  通过 subprocess.run 在独立进程中执行，避免与 Gradio 主进程的 DDS 冲突。
  超时设为 20 秒。
  文件: gradio_panel.py → reset_arms()

================================================================================
七、进程管理 — SIGHUP 问题
================================================================================

【问题现象】
  从 Gradio 面板 Stop Teleop 后，teleop 子进程被 SIGHUP 信号杀死，
  来不及执行安全退出流程（go_home）。

【修复】
  在 teleop_hand_and_arm.py 顶部添加:
    signal.signal(signal.SIGHUP, signal.SIG_IGN)
  忽略 SIGHUP，确保子进程在父进程退出后仍能完成安全退出。
  文件: teleop_hand_and_arm.py

================================================================================
八、网络接口配置
================================================================================

【坑】
  Unitree DDS 通信需要指定正确的网络接口名。
  本机的以太网接口是 enp2s0（不是 enp3s0）。
  ChannelFactoryInitialize(0, "enp2s0") — 第二个参数必须匹配。
  如果写错，DDS 会报 "does not match an available interface" 并静默失败，
  表现为发布的消息永远到不了机器人。

================================================================================
十、经验总结
================================================================================

  1. DDS + multiprocessing.Process = 大坑
     DDS 库在底层维护 socket fd，fork 后父子进程共享同一 fd，
     导致 Publisher 行为不可预测。解决方案: 用 threading.Thread 替代。

  2. 重力补偿要区分关节
     arm_sdk 模式下手臂 PD 控制已足够，不要叠加重力补偿 tau，
     否则会导致力矩爆炸。只对腰部等被动关节施加重力补偿。

  3. 安全运动序列至关重要
     启动和停止时都必须有"外展 → 目标 → 释放"的过渡序列，
     否则手臂直线运动会穿过身体造成碰撞。

  4. 硬件故障的表现: 电机状态值异常大（如 -238），断电重启可恢复。

  5. 网络接口名写错 DDS 不会报错但通信完全失效，排查时优先确认。

  6. SIGHUP 信号: 从 Gradio subprocess 管理的子进程，父进程退出时
     子进程会收到 SIGHUP 被杀，必须显式忽略才能完成清理工作。

  7. Relax Arms 需要检测当前状态: 如果手臂已经放松，不应再次接管控制
     并外展，否则会把已放松的手臂重新拉起来卡住。
